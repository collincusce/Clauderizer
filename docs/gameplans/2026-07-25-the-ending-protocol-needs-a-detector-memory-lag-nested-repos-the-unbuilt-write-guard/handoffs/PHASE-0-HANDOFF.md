**L-51.** Before any irreversible release step (tag → GitHub Release → PyPI publish), gate on three sweeps. (1) A version number is a claim across four registries that never sync — source (pyproject/__version__), remote git tags, GitHub Releases, the PyPI index — plus the ordering invariant that origin/main must hold the staged commit BEFORE any tag/Release (a GitHub-UI release tags the REMOTE head, so locally-authored guards are unpushed by construction); sweep all four with fresh eyes (uvx by-name answers from uv's cache and can hide a failed attempt — v0.7.0/v0.8.0 were double-claimed by exactly this). Build the adversarial measuring-stick FIRST: (a) an eval concludes only what its fixtures permit — a cleanly-separable corpus saturates at the 1.0 ceiling so no scoring change can show lift (proves "no regression", never "no value"), so target the mechanism with length-bias/term-skew/near-duplicate confounds up front; (b) when you author BOTH fixture and detector, a 100%-detection/0-FP result is suspicious by construction (teaching to the test) — seed adversarial NEAR-MISSES and run a NAIVE strawman beside the real detector, credibility = beating the strawman ON the near-misses, not beating a no-check baseline (anything beats zero); (c) an audit finding names a symptom + a HYPOTHESIZED cause — measure the hypothesis before fixing (a predicted tokenizer under-count was falsified; the real defect was incoherence, fixed by single-sourcing, not by lowering a threshold to manufacture pairs); (d) near-DUPLICATE detection length-normalizes overlap (Jaccard |A∩B|/|A∪B|), never the raw count (the relevance signal) that a long distinct entry trips by sheer size. ## Phase Notes (agent-owned)

# WHY THIS GAMEPLAN EXISTS

1.14.0 shipped on 2026-07-25 and its own execution produced the argument for
this patch. Read the 1.14.0 POST-MORTEM before starting — sections "What the
Gameplan Got Wrong" items 3, 4 and 5 are the whole case.

**The founding claim of this product is that conventions rot because they rely
on the agent remembering, and that Clauderizer's answer is rituals that
EXECUTE.** That answer is applied unevenly, and 1.14.0 measured the cost three
separate ways in a single session:

1. **The memory fell two phases behind the work.** Phases 5 and 6 were
   implemented, tested and pushed across EIGHT commits while the tracker still
   read them not-started. Nothing emitted a signal. It was corrected only
   because the user announced a session switch — had they closed the terminal,
   the next session would have inherited a corpus describing work that no longer
   matched the repo, and would not have known a release was staged. Every OTHER
   discipline has a detector (cascade_hygiene, unchecked exit criteria,
   unresolved open items, corpus redundancy, wiring drift). The one that keeps
   memory current has none. → **H-22, Phase 0.**

2. **Two nested clauderized repos contradicted each other.** `/home/ccusce` is
   itself a clauderized repo containing this one, so TWO SessionStart digests
   fired and the first announced "No active gameplan" about a repo mid-release.
   That was the first thing in the executing session's context and it read past
   it for the entire release; a second, colder session flagged it before it
   could report state. INVARIANT-08's at-most-once guarantee is enforced by an
   in-memory per-process signal, which nesting defeats structurally.
   → **H-23, Phase 1.**

3. **A guard was specified as an exit criterion and never built.** 1.14.0's
   Phase 5 criterion 12 required a write-time guard rejecting tool-call markup
   in structured-write arguments. `grep` for it in mutations.py returns zero.
   FOUR malformed writes now sit in append-only memory, the fourth landing while
   the finding about the first three was being recorded. Inside the release
   whose thesis is that written intent without an executable check rots.
   → **Phase 2.**

D-069 is the decision that generalizes these: a discipline this system asks an
agent to perform must have a machine-checked signal that notices when it has not
been performed, or it is a hope. Its standing test — name the detector at design
time, or say plainly the practice is unenforced — is what Phase 4's post-mortem
has to grade honestly.

## Phase 0 specifics

**What exists:** `rituals/status_bundle.py` builds the digest and already reads
phase rows; `rituals/preflight.py` has the check framework and an advisory
downgrade path (`preflight_advisory`); `release_check._git` is a working example
of shelling to git safely with a timeout.

**What does not:** any comparison between tracker state and repo state. The
digest asserts a phase state from the tracker and never reads the commits that
would contradict it — D-065's thesis, turned inward on the tool itself.

**Constraints:** advisory only, never blocking (INVARIANT-05); no config key
(D-015); zero bytes when there is no lag (INVARIANT-08); hooks stay read-only
and exit 0 (INVARIANT-06). Derive the claim from git, not from a persisted
counter.

**The honest test** is criterion 7: run the detector against this repo's own
history at `eac1c9a` and assert it would have fired. If it would not have
caught the failure that motivated it, the design is wrong.
