# Chat Handoff Index — the ending protocol needs a detector — memory lag, nested repos, the unbuilt write guard

> Last updated: 2026-07-25
> Status: Phase 4 of 6 in progress

## How This Works

This is the coordination point for sessions executing this gameplan. A fresh
session gets current state automatically from the Clauderizer SessionStart hook,
then calls `cz_next_phase_context` for the active phase. No manual reading order.

## Pre-Flight Verification

Run `cz_preflight` before any code. If any enabled check fails: STOP, report.

**Current baseline test count**: 1074

## Ending Protocol

1. `cz_transition_phase` the finished phase to complete.
2. `cz_add_output` each concrete produced value; `cz_add_phase_summary` the recap;
   `cz_add_correction` / `cz_add_lesson` as earned.
3. `cz_transition_status` on touched entities (fires cascade); `cz_resolve_cascade`
   the verdicts.
4. `cz_write_handoff` for the next phase.
5. Run exit verification; report the test count.

## Per-Phase Completion Summaries

### Phase 0 — completed 2026-07-25

Built the detector the ending protocol never had (H-22, D-069). `rituals/memory_lag.py` answers one question — does the tracker still describe the repo? — and it answers it from git rather than from the tracker asserting itself (D-065). The anchor is the last commit that TOUCHED the phase tracker, which is "the last recorded state change" read as evidence instead of trusted as a date someone typed into a cell; work is commits past that anchor touching anything outside the docs tree and `.clauderizer/`; lag is work landing while the tracker still reads the phase unstarted. It surfaces as a conditionally-emitted `⚠ Memory lag:` digest line naming the phase and the commit count, and as a `cz_preflight` **warn** carrying the identical sentence from `memory_lag.describe` — one claim, one wording, two surfaces, pinned by a test (L-55). Advisory throughout: it never fails pre-flight and never blocks a transition (INVARIANT-05), it is read-only and swallows exceptions so a hook can call it (INVARIANT-06), and it emits zero bytes when memory is current, which the existing golden digest gate plus a new git-present-vs-git-absent byte-identity test both hold (INVARIANT-08). No config key, no persisted flag.

The scope gate is the design decision worth flagging forward: the detector fires only when the tracker claims a phase has NOT begun. An in_progress phase is supposed to accumulate commits, so firing there would have made it noise, and noise gets ignored — but the honest cost is that a phase left marked in_progress long after it was truly finished is not detected, because git cannot tell "still working" from "done but unrecorded". That limit is written into the module docstring and the H-22 resolution rather than papered over. Evidence: 11 tests, suite 1074 → 1085. RED was demonstrated substantively, not just by ImportError — a probe built the lagging fixture and ran it against the pre-1.14.1 engine at efdf210, which reported a clean `preflight PASS` and no line at all while a `src/` commit sat past a NOT STARTED phase. The historical test replays this repo's own `eac1c9a`, parsing the phase state from the tracker as it stood at that commit, and asserts the detector fires on the failure that motivated it. Then it caught its own author: with phase 0 still reading READY after commit 61317f5, `clauderize status` named it.

### Phase 1 — completed 2026-07-25

Two clauderized installs stop narrating over each other (H-23). The pathology was structural, not a bug in either install: `/home/ccusce` is itself a clauderized repo containing `/home/ccusce/Clauderizer`, both hooks fire for a session in the inner repo, and each is perfectly correct about its *own* repo — which is how "No active gameplan" ended up as the first line of a session that was mid-release. INVARIANT-08's at-most-once guarantee could not help, because it is an in-memory per-process signal and these are two processes. A shared flag would have been the obvious fix and the wrong one: that is persisted cross-process state, which INVARIANT-05/08 rule out.

`src/clauderizer/nesting.py` reframes it as **ownership**. For any session cwd exactly one install owns it — the nearest clauderized ancestor — and a non-owner stays silent. Nothing is remembered: the decision is recomputed from the hook payload's `cwd` on every event, so there is no flag to fall out of date, and it is threaded through *every* handler rather than just SessionStart, since otherwise the outer install simply re-enters context through `UserPromptSubmit`. Scope is deliberately narrow to protect INVARIANT-07: an install falls silent only when the session's owner is a *proper descendant* of its own root, so a session elsewhere on the machine — or a host that sends no `cwd` at all — behaves byte-identically to 1.14.0. Both directions of the relationship are now reported, because neither was visible anywhere: `doctor` names nested installs by path and, from inside, the clauderized ancestor; `init` under an existing install warns and proceeds, since nesting is legal and only the silence was the problem.

Evidence, 16 tests, suite 1085 → 1101. Applying this gameplan's own Lesson 2, the RED was substantive rather than an ImportError: a probe built the two nested repos and fired SessionStart the way the wrapper does, and the pre-1.14.1 engine returned **two** digests where the fixed engine returns one. Live on this machine, the outer install — still running the published 1.14.0 — emits `[Clauderizer] No active gameplan.` for a session in the inner repo, while the same payload against the 1.14.1 engine is silent with exit 0 and only the inner install speaks. The live scan turned up something the plan did not anticipate and worth carrying forward: **ten** nested installs under `/home/ccusce`, because `/home/ccusce/.claude/settings.json` *is* the per-user settings file — clauderizing `$HOME` makes that install's hook global to every session on the machine. One honest gap remains, recorded as output DEPLOYMENT_GAP: the outer hook runs `uvx --from clauderizer`, so the repair reaches it only once 1.14.1 publishes, and Phase 4 must re-run this check after the publish.

### Phase 2 — completed 2026-07-25

Built the guard 1.14.0 specified as an exit criterion and never shipped. `mutations._strip_toolcall_markup` now runs inside `_safe_body` and `_one_line` — the D-066 render boundary every `cz_*` write already flows through, so it is on the path rather than merely available, which is the distinction the four corrupted entries exist to prove. The design question was what counts as "tool-call markup" without eating legitimate content, and the answer that survived is two unambiguous signals rather than a field-name blocklist: the tool-call vocabulary itself (`parameter` / `invoke` / `function_calls`, bare or `antml:`-prefixed), and an **unbalanced** closing tag — `</context>` with nothing opening it. Unbalanced-detection is what lets a body legitimately containing `<div>…</div>` through completely untouched, a promise no blocklist of field names could make; and code spans and fenced blocks are skipped, matching the read side's `sections._without_code_spans`, so an entry that quotes this very shape — as this repo's CHANGELOG and tests now do — is never rewritten. Per D-066 it normalizes rather than rejects: the tags are pure scaffolding, so removing them loses no content (INVARIANT-03) and no mutation gains a hard block (INVARIANT-05).

The acceptance corpus is read off disk, not synthesized. The tests locate D-052, D-062, H-19 and H-23 in the live registers, first assert the stray tag is *still there* — a standing guard against a future phase quietly "cleaning" append-only memory — and then assert the guard neutralizes it while every word of prose survives. The RED demonstration was substantive rather than an ImportError (this gameplan's Lesson 2): feeding the pre-1.14.1 engine the exact live argument shapes reproduced the corruption byte-for-byte, `**Context**: …</context>` followed by a swallowed `<parameter name="context">` line, which is precisely `docs/DECISIONS.md:381-382`. One piece of pre-existing drift closed along the way: the D-066 boundary shipped in 1.14.0 with no entry in `docs/subsystems/mutations.md` at all, so the new section documents the whole boundary — forged structure, table cells, marker blocks and now leaked tool-call markup — not just this phase's addition. Suite 1101 → 1127.

### Phase 3 — completed 2026-07-25

Closed the two items carried out of 1.14.0, which turn out to be the same defect wearing different clothes: a component reporting a clean result from evidence it never read. `model.from_file` returned a bare `None` for an unreadable entity doc — byte-identical to the value it returns for ordinary prose — so a BOM'd entity (the L-24 class, since PowerShell and several Windows editors write UTF-8 BOM by default and the frontmatter fence anchors at offset zero) did not fail, it silently *stopped existing*. It now returns one of three things, and the third is the point: a `Drop` carrying the path and a machine-readable reason. `graph.index.build` accumulates drops and duplicate-id collisions (last-wins preserved, so no existing graph changes shape — the shadowed file is merely no longer invisible), `Graph.integrity()` publishes the accounting identity `entities_indexed + dropped + collisions == entities_on_disk`, and both `cz_corpus_health` (as `graph_integrity`, with a `GRAPH FAULT` summary prefix) and `clauderize doctor` name every offender by path. Drop classification is deliberately conservative — a doc with no frontmatter, or with frontmatter carrying neither `id` nor `type`, reports nothing — because a count with standing false positives is a count nobody reads.

The payoff lands at the consumer, and it is the criterion worth reading twice: `cz_cascade` on an entity not in the graph used to return `ok:true` with zero dependents, which is indistinguishable from a real leaf. A dropped doc therefore read as *safely cascaded*, and D-018 was void with nothing anywhere saying so. It now returns `ok:false`, explains why "0 dependents" would have been a false all-clear, and — when a drop plausibly explains the missing id — names that drop as the cause. The RED demonstration is the whole argument in four lines: on the pre-1.14.1 tree the same BOM'd file produced `from_file -> None`, absent from the graph, and `cz_cascade -> ok=True, 0 direct, 0 transitive`.

Task 4.6 closes alongside it: `init` spawn-tested the commands composed at step 0b but never `PORTABLE_COMMAND`, the wiring it actually writes to `.mcp.json` — so it certified wiring it did not write and wrote wiring it never certified. That probe now runs, and its verdict is deliberately **advisory** rather than a `WiringRefused`: the portable form is `uvx --from clauderizer[mcp]`, which needs the network on a cold cache, and an offline or proxied first run must still install and simply learn in-band that this leg is uncertified. Suite 1127 → 1152, no regressions.

### Phase 5 — completed 2026-07-25

Added mid-flight (A-002) after a live failure in this very session: asked to "take care of the dream notes", I ran the DREAMER — capturing more notes and staging four proposals nobody requested — when the ask was to TRIAGE what the dreamer had already produced. The correction named the real defect precisely: the two halves of the loop share a name, so the instruction was ambiguous and I resolved it wrong.

The fix is lexical, and the design rule it follows is that each artifact must carry its own noun *and* its own verb, in every place a human or agent reads it. Raw **notes** are **dreamed**; staged **proposals** are **triaged**. The digest's note line now says so and explicitly denies the other reading ("— not triage"); the proposal line states the A-001 gate affirmatively ("Further DREAMING is blocked until the dream proposals are triaged") where it previously said only "to unblock cz_dream", which reads as an optional benefit rather than a rule. The skill's description maps trigger phrases to halves and lists the exact phrasing that misrouted this session as a TRIAGE trigger, and its body opens with a two-row artifact table before any instructions. README gains a glossary row per artifact. Zero behavior change: `cz_add_dream`, `cz_dream`, `cz_dream_propose` and the triage ops keep their semantics and gating — this phase changed what things are called, not what they do.

Two things worth carrying forward. First, the asymmetry that makes this worth a phase rather than a wording tweak: triage is idempotent and reversible, while a dreaming pass advances an append-only watermark, so the notes it consumes cannot be un-consumed — the ambiguity is not merely confusing, it is *destructive in one direction*, which is why the skill now says to ask when the ask is unclear. Second, writing the tests exposed two of my own assertions passing for the wrong reason: "block" matched the word *unblock*, and "the description mentions both words" was already true of the description that misrouted the session. Both were tightened to test the actual distinction before any code changed — a small instance of the same discipline the whole gameplan is about. Along the way `docs/features/dream-loop.md` turned out to still be the `_(describe.)_` scaffold placeholder, and `tests/test_dream_vocabulary.py::test_skill_source_and_render_are_identical` is the first test anywhere pinning a skill's src/ template against its .claude render (L-55 seam 1, previously unenforced for the entire skills surface). Suite 1152 → 1164.

### Category: Process

**1.** A drift detector earns its line in the digest by being QUIET, and quiet comes from gating on the state that asserts nothing-has-happened — not from tuning a threshold. Memory-lag fires only where the tracker claims a phase has not begun; gating instead on "in_progress phase with N commits" would fire on every normal working session, and a detector that cries wolf is worth less than none. Two corollaries. (1) Anchor the claim to the artifact's own git history — the last commit that TOUCHED the tracker — never to a date cell the writer typed, so the signal is evidence read rather than the tracker vouching for itself (D-065); this also makes "the same repo with the state recorded produces nothing" fall out for free, because recording it moves the anchor. (2) State the scope limit in the module docstring and the finding resolution instead of widening the claim to cover it: git cannot distinguish "still working" from "done but unrecorded", so a stale in_progress phase is undetectable, and saying so is stronger than a fuzzy staleness score that pretends otherwise. *(evidence: Phase 0, commit 61317f5: src/clauderizer/rituals/memory_lag.py UNSTARTED_STATES gate; tests/test_memory_lag.py::test_silent_for_an_in_progress_phase pins the quiet case, ::test_silent_once_the_tracker_records_the_work pins the anchor-moves case; H-22 resolution records the limit)*

**3.** When two independent installs of the same tool both fire for one session, the fix is OWNERSHIP, not coordination. The instinct is a shared "someone already spoke" flag — but that is cross-process persisted state, and the correct question is not "did anyone speak?" but "whose session is this?". Derive a single owner from the data every process already has (here: the nearest clauderized ancestor of the payload's session cwd), recompute it per event, and let non-owners fall silent. No flag, no file, nothing to go stale, and it works identically for two installs or ten. Two things this discipline forces: (a) thread ownership through EVERY handler, not just the loud one — the outer install would otherwise re-enter context through UserPromptSubmit after being silenced at SessionStart; and (b) scope the silence to the exact pathology (owner is a PROPER DESCENDANT of my root) rather than to "any session that isn't mine", because the broader rule quietly breaks anyone who wired a global hook deliberately. *(evidence: Phase 1, commit 439dd1b: src/clauderizer/nesting.py outranked_by; tests/test_nested_installs.py::test_every_event_honors_ownership and ::test_unrelated_session_cwd_is_unchanged pin (a) and (b); ::test_ownership_is_not_persisted pins the no-flag property)*

**5.** When a guard must reject a CLASS of malformed input, look for the structural property that separates it from legitimate content, not for a list of the bad values. The obvious implementation here was a blocklist of structured-write field names (</context>, </impact>, …), which is both incomplete (every new tool argument adds a name) and destructive (a lesson discussing XML loses content). The structural property is BALANCE: leaked framing is an unbalanced closing tag, real markup in prose is balanced. That one predicate is complete, needs no maintenance as the tool surface grows, and provably cannot touch well-formed content. Pair it with the vocabulary that is unambiguous on its own (parameter/invoke/function_calls) and with a code-span exemption, so an entry that QUOTES the bad shape — documentation, tests, changelog — survives; the read side already established that exemption, and a write-side guard without it will eventually corrupt the very docs that describe it. *(evidence: Phase 2: src/clauderizer/mutations.py _strip_toolcall_markup (unbalanced-closer predicate + _code_segments); tests/test_toolcall_write_guard.py::test_balanced_markup_is_left_alone, ::test_markup_inside_a_code_span_is_untouched, ::test_an_opener_and_its_closer_may_straddle_a_code_span)* (promoted 2026-07-25: L-63)

**6.** A function that returns the same value for "nothing here" and "this failed" has no failure mode — it has a silence. model.from_file returned None both for ordinary prose and for an entity doc it could not read, so a defective node did not error, it stopped existing, and every downstream consumer reasoned about a DAG that was quietly short a node. The repair is a three-way return (value / absent / DROP-with-reason), and the two disciplines that make it worth anything: (1) the failure record must carry the PATH and a machine-readable reason, because a count is not actionable — "1 entity doc not indexed" sends nobody anywhere; (2) publish an ACCOUNTING IDENTITY (indexed + dropped + shadowed == files seen) so a caller can prove nothing fell out between the scan and the report, rather than trusting that it didn't. And classify conservatively: only a file that clearly INTENDED to be the thing counts as a failure, or the count acquires standing false positives and stops being read. The payoff is never in the loader — it is at the consumer that was answering confidently from the gap (cz_cascade's "ok:true, 0 dependents" for a node that was never in the graph). *(evidence: Phase 3: model.Drop + _classify_drop; graph/index.py Collision + Graph.integrity(); ops.cz_cascade unknown-entity guard. RED at efdf210: a BOM'd subsys.probe gave from_file->None and cz_cascade->ok=True with 0 dependents)*

**8.** Two operations that consume different artifacts must not share a name — and when one of them is IRREVERSIBLE, the naming is a safety property, not a style preference. The dream loop has raw NOTES (dreamed) and staged PROPOSALS (triaged); both were called "dreams", so "take care of the dream notes" ran the dreamer instead of the triage, consuming notes against an append-only watermark that cannot be rewound. Triage would have been idempotent; the wrong guess was not. The rule: give each artifact its own noun AND its own verb everywhere a human or agent reads it (status line, skill trigger, glossary, docstring), have the ambiguous-but-common phrasing listed explicitly as a trigger for the SAFE half, state any gate affirmatively rather than as a reward ("dreaming is blocked until triaged", never "triage to unblock dreaming"), and instruct the agent to ASK when the ask is genuinely ambiguous and one branch is destructive. Corollary for testing prose: assertions on wording pass for the wrong reason with alarming ease — "block" matches "unblock", and "mentions both words" was already true of the text that caused the incident. Assert the DISTINCTION (each noun adjacent to its own verb; the line's subject), not the presence of vocabulary. *(evidence: Phase 5 / A-002, live in-session failure and correction; tests/test_dream_vocabulary.py (two assertions tightened after passing for the wrong reason); status_bundle.render_digest both dream lines)*

### Category: Testing

**2.** "Demonstrated RED on the pre-fix tree" is satisfied by an ImportError only in the letter. A new module means the new test file cannot even collect on the old tree, which proves the module is absent — not that the BEHAVIOR was absent, which is the thing the criterion is actually about. Build the red demonstration as a standalone probe that uses ONLY APIs present on both trees, drives the same fixture the tests build, and prints the old engine's actual answer. Here that turned a collection error into the real finding: the pre-1.14.1 engine reported `preflight PASS` and a digest with no lag line, against a repo whose tracker read NOT STARTED with a src/ commit sitting past it — the 1.14.0 failure reproduced on demand, in the old engine's own words. Run the same probe post-fix and the two outputs are the before/after the phase summary needs. Prefer `git clone --local --no-checkout` + `checkout --detach` over `git worktree add` for the isolated old tree: a clone writes nothing into the real repo's .git, so the isolation is structural rather than promised (L-29). *(evidence: Phase 0: scratchpad red_probe.py run under PYTHONPATH=<clone>/src at efdf210 vs the working tree; recorded in output RED_BEFORE_GREEN_HARNESS)*

**4.** Run the detector against the REAL machine, not only the fixture — the fixture proves the mechanism, the machine tells you the size of the problem. The two nested fixture repos proved ownership works; pointing the same scan at the actual home directory found TEN nested installs and surfaced the root cause the gameplan had not stated: /home/ccusce/.claude/settings.json IS the per-user settings file, so clauderizing $HOME makes that install's hook global to every session on the machine. Corollary for anything wired through a package runner: a live green on the mechanism is NOT a live green on the deployment. The outer install's hook runs `uvx --from clauderizer`, i.e. the PUBLISHED engine, so the repair does not reach the very install that exhibits the pathology until the release ships and the runner's cache refreshes — record that gap as an explicit output and re-run the live check after publish, rather than letting "verified live" read as done. *(evidence: Phase 1 outputs LIVE_NESTED_SCAN (10 installs, 0.24s) and DEPLOYMENT_GAP; /home/ccusce/.clauderizer/hook.sh line `uvx -q --from clauderizer clauderizer-hook`)*

**7.** Before closing a phase, RUN what it built against THIS repo, not only against fixtures. A fixture proves the logic; only the live run proves the whole chain — config load, tracker parse, evidence gathering, render — fires in a real session (L-07's in-band evidence rule). The memory-lag detector caught its own author this way within a minute of existing: with the phase committed and the tracker still reading READY, `clauderize status` named the phase and the commit count, which eleven passing tests could not have shown. It happened because I tried it, not because anything asked — exactly the kind of practice D-069 says needs a detector or an honest "unenforced". Corollary from the same release, and the sharper half: a live green on the MECHANISM is not a live green on the DEPLOYMENT. When the thing runs through a package runner against a PUBLISHED build (uvx, npx, pipx), the install that exhibits the bug keeps exhibiting it until the release ships and the runner's cache refreshes — so record that gap explicitly and re-verify after publish, rather than letting "verified live" read as done. *(evidence: gameplan 2026-07-25: Phase 0 output LIVE_DOGFOOD (the detector naming its own commit) and Phase 1 output DEPLOYMENT_GAP (the outer install still running the published engine via uvx))*

**9.** Before building on a field of someone else's payload, CAPTURE ONE. Phase 1's whole nesting fix keys off payload["cwd"], and cwd turned out to be the only key nothing else in the engine reads — hook_event_name, source and prompt are proven by shipped handlers, cwd was an assumption with a full phase resting on it. Had the harness not sent it, the feature would have shipped inert and looked correct in every test, because the fixtures supply the key by construction. The capture is cheap and non-invasive: a gitignored per-user settings file with a SessionStart/UserPromptSubmit hook whose command is `tee <file> > /dev/null` (silent, exit 0, zero effect on the session), then one real session, then replay the captured bytes through the real code path and delete the probe. Measured shape for Claude Code: SessionStart {session_id, transcript_path, cwd, hook_event_name, source}; UserPromptSubmit adds {prompt_id, permission_mode, prompt}. This is L-54's "verify the reality first" and L-25's "capability, not presence" applied to an input contract rather than a command — and the tell that you need it is exactly this: your feature is the only reader of that field. *(evidence: Phase 1 output PAYLOAD_CWD_VERIFIED; captured live via a gitignored .claude/settings.local.json probe and replayed through hook.dispatch for both the outer (silent) and inner (speaks) anchors)*
